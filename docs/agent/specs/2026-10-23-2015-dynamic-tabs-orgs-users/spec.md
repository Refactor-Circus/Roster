# Registered tabs on organization and user screens

Ticket: [#4](https://github.com/Refactor-Circus/Roster/issues/4)

## Goal

Hosts and other packages can register their own tabs on Roster's Atrium organization and user screens, so app data (for example an "Orders" tab) shows in context of the record, only for viewers allowed to see it.

In-scope enablers, and only these: the organization screen's tab nav extracted into a shared partial that both screens render, and an `overview` tab on the user screen that wraps the current page content (only while a user tab is visible). The user screen's redirects are unchanged (D-020): they carry no `tab=` parameter and no tab visibility check runs while building a redirect.

## Acceptance criteria

1. `RefactorCircus\Roster\Atrium\Tabs` is bound as a singleton in `RosterServiceProvider::register()` (`app(Tabs::class) === app(Tabs::class)`); `app(Tabs::class)->organization(TabDefinition)` and `->user(TabDefinition)` register a tab and return the registry (D-005). Registration works from a host provider's `boot()`; the registry is read lazily when a screen renders, so a tab registered after another provider booted, but before the request renders, shows. Registration belongs in `boot()`, not in `register()` (the singleton may not be bound yet) and not in request-time code (middleware, controllers); the README says so.
2. `TabDefinition::make($key)` builds a tab with fluent `label()`, `icon()`, `view()` / `component()` (setting one clears the other), `resolve(Closure)`, `permission(string)`, `authorize(Closure)` and `public()` (D-024). Observable state: `key`, `label`, `icon`, `view`, `component`, `permission` and `public` (bool, default `false`) are publicly readable; `label` defaults to the key and `icon` to `squares-2x2`; after `view('a')` then `component('b')`, `view` is null and `component` is `'b'`, and the reverse holds. Assigning to `$tab->label` (or any property) from outside throws `Error`. `resolver` and `authorize` are private (D-012): they are used only through `resolveData()` and `allows()`, and reading either from outside throws `Error`.
3. Keys must match `^[a-z0-9][a-z0-9._-]*$` (D-009); registration throws `InvalidArgumentException` for any other key. Registering an organization tab whose key is a built-in organization tab, or a user tab whose key is `overview`, throws `InvalidArgumentException`; so does registering the same key twice on one screen, or a definition with neither a view nor a component. Reserved organization keys come from the public constant `Tabs::ORGANIZATION_TABS`, a list of keys only (D-023); `OrganizationUiController` keeps its own private permission map keyed by those keys, and a unit test asserts the two key sets match, so the constant stays the one source of keys (`members`, `teams`, `invitations`, `roles`, `sso`, `scim`, `mcp`, `activity`, `settings` today). A unit test loops that constant and asserts each key is rejected and that the exception message names the key, and a controller test asserts the built-in tab bar shows exactly the keys of that constant that the viewer may see. Reserved keys apply even when the built-in tab is conditionally offered, so `activity` is rejected when Keen is absent and `mcp` when MCP is off. Registering a duplicate key throws an `InvalidArgumentException` whose message names both the key and the screen (`organization` or `user`), tested. `Tabs` stores a clone of the definition at registration, so later fluent calls on the host's instance (`view()`, `component()`, `label()`, `icon()`) cannot bypass validation or change the registered tab; a test mutates the original after registering and asserts the registered tab is unchanged. Tests cover an accepted `acme.billing` and rejected uppercase, space, slash and empty keys. The pattern admits all-digit keys, which PHP turns into int array keys: `Tabs` casts keys with `(string)` wherever it reads them back (`array_keys`, the visible-key list, the `?tab=` lookup), and a test registers `123` and `007`, checks the bar, `?tab=123` and `?tab=007`, and, with `assertViewHas('tab', '123')` / `'007'` (strict string comparison), that the key reaches the view as a string. The README states that new built-in tab keys may be added in minor releases and recommends `vendor.key` for registered tabs.
4. `Tabs` has a `flush()` that forgets every registered tab, documented as for tests only; there is no per-key unregister or replace at runtime. The Roster UI test case calls `Tabs::flush()` in `beforeEach` and `afterEach`, and a unit test registers a tab, flushes, and asserts `organizations()` and `users()` are empty.
5. Registration always validates and stores, whether or not `roster.ui.enabled` is on; with the UI disabled the tabs simply never render. A test registers a valid tab with the UI disabled (no exception, tab listed by `organizations()`) and an invalid one (throws).
6. On the organization screen, registered tabs show in the tab bar after the visible built-in tabs, in registration order, with their label, icon and `data-testid="tab-{key}"`. The label and icon render escaped (never `{!! !!}`); a test registers a label containing markup and asserts it appears escaped. The icon is passed to Atrium's icon component as a name only. Verified: `Atrium\Support\Icons::svg()` throws `InvalidArgumentException` for an unknown name, and `Icons::has($name)` exists. An unknown icon name must not break the screen: at render Roster checks the name with `Icons::has()` and uses `squares-2x2` when Atrium doesn't know it (D-017), tested directly: the observable is the response HTML, where the unknown-icon tab's icon markup equals the markup of a tab registered with `squares-2x2`. Never wrap Blade rendering in try/catch. A test registers a tab with an unknown icon and asserts the screen answers 200, built-in tabs still render and the registered tab is in the bar. With three registered tabs where the middle one is hidden from the viewer, the test asserts order against the exact strings `data-testid="tab-a"` and `data-testid="tab-c"` (via `assertSeeInOrder`, using keys that are not substrings of each other) and `assertDontSee('data-testid="tab-b"')`, and asserts the first registered tab appears after the last visible built-in tab.
7. `?tab={key}` on the organization screen renders the registered tab's view or component with `organization` and the resolver's data. The resolver receives the organization and runs only after the access check passes, and only for the open tab: a feature test (`tests/Feature/Ui/OrganizationRegisteredTabsTest.php`) uses a counting resolver and asserts it is called once for `?tab={key}`, and zero times for `?tab=members`, for no `?tab=`, for a registered key the viewer may not see, for an unknown key, and for a non-string `?tab=`. Roster's variables always win over resolver data (D-010): the registered-tab partial receives exactly `organization` / `user`, `tab`, `tabs`, `registeredTab` and `errors`, built by spreading resolver data first and Roster's keys last. A test has a resolver return `tab`, `tabs`, `registeredTab`, `errors` and `organization` / `user` and asserts the tab bar, record, definition and validation errors are Roster's. On the component path the resolver data is passed as a single `data` prop, not spread into attributes, so keys such as `slot`, `attributes` or a key containing a dash cannot break the component; on the view path the README lists the reserved names (`__env`, `app`, `loop`, `errors` and the five above). A test has a resolver return `slot`, `attributes` and a dashed key and asserts the screen answers 200.
   Authorization comes first: the screen's own authorization (including its 403/404) runs before any `authorize` closure, visibility check or resolver, so host code never runs for a viewer denied the screen. A test on each screen uses counting `authorize` and resolver closures with a viewer denied the screen and asserts zero calls.
8. The organization screen's default tab is chosen from the visible built-in tabs only, keeping today's `settings` fallback; registered tabs never become the default. A test uses a viewer who can see no built-in tab but does see a registered one, and asserts the open tab is `settings` as today.
9. A tab with `permission('x')` is offered on the organization screen only when `ScreenAccess::allows('x', $organization)`; on the user screen only when `ScreenAccess::allows('x', null, $user)` (D-006). A tab with `authorize(fn (Request $request, Model $record): bool)` is offered only when the closure returns `true`; with both a permission and a closure, both must pass; a tab with neither is hidden unless it calls `public()`, which makes it visible to anyone who may open the screen (default-deny, D-024). Tests cover permission-only, closure-only, `public()`, neither (hidden, `?tab=` 403), both pass, one fails and neither passes, on both screens, with the bar and `?tab=` (403) asserted for each hidden case. A test also uses a permission string that nothing grants and asserts the tab is hidden. An `authorize` closure that throws counts as denied (D-015): the tab is hidden, `?tab=` answers 403, the exception goes to `report()` once per request per tab key, and the screen renders (200 on the default tab). Tests use `Exceptions::fake()` and a counting throwing closure on a request that renders the bar and checks `?tab=`, and assert both that the exception was reported exactly once and that the closure ran exactly once (so the test fails if the memo does nothing), the 200 status and the tab's absence from the bar. Closures run lazily: `authorize` closures are evaluated only for a tab registered on that screen, after the screen's own authorization passes; a test registers none and asserts zero closures run on both screens. The visibility results and the reported-key set never live on `Tabs` or `TabDefinition` (both are long-lived and would leak across requests under Octane and queue workers, possibly showing a tab to the wrong viewer); they live in a memo class bound with `scoped()` in the container, so it is rebuilt per request and is Octane-safe (D-018). The memo is keyed by screen (`organization` / `user`), record key and tab key, so the same tab key on both screens, or on two records, never shares a result. A `scoped()` binding is only reset by Octane and queue workers, not between sequential `$this->get()` calls in a Testbench app, so the tests reset it explicitly with `app()->forgetScopedInstances()` between requests. A test makes two sequential requests in one process with different viewers, calling `app()->forgetScopedInstances()` between them, and asserts visibility is re-evaluated for each and the exception is reported once in each. `allows()` receives the current request whatever its method, so `authorize` closures must not assume GET (README says so). A throwing resolver propagates (D-015), pinned by a test. The README documents that `authorize` closures run on every render of the screen, so they must be cheap and must not throw, and that resolver and view errors surface as page errors.
10. Requesting a registered tab the viewer may not see with `?tab=` answers 403 on both screens (D-007). Visibility (permission and closure) is evaluated once per request and reused for the tab bar and the `?tab=` check. The `?tab=` value is read as a string only (`is_string($request->query('tab')) ? ... : null`) in both controllers; a non-string value such as `?tab[]=x` or `?tab[a]=b` is treated as absent. A `?tab=` key that is neither built-in nor registered, or a non-string `?tab=`, falls back to the screen's default tab with 200 on both screens (D-013), with no resolver running. Feature tests cover an unknown key and `?tab[]=x` on both screens, each expecting 200, the default tab, and zero resolver calls; the organization screen's unknown-key case is the regression test for today's behaviour.
11. The user screen has one rule (D-014): the tab bar and the `overview` wrapper exist if and only if at least one user tab is visible to this viewer. With no user tabs registered, or with tabs registered but all hidden from the viewer, the response has no element whose `data-testid` starts with `tab-` (`assertDontSee('data-testid="tab-')`), the page is unchanged and every existing user screen assertion passes unchanged; `?tab={hidden key}` still answers 403 (D-007), and `?tab=overview`, `?tab=` and unknown keys all render the unchanged page with 200. The full user screen feature suite runs as a dataset over two states, "no tab registered" and "one visible tab registered" (in the second state only assertions about the tab bar differ), so both states are covered by the same assertions.
12. When at least one user tab is visible (criterion 11's condition), the user screen shows a tab bar in the organization screen's style (D-008) whose first tab, `overview`, holds all of the current page content unchanged (including the Actions column, danger zone, history and impersonation controls) and is the default. `?tab={key}` renders the registered tab with `user` and the resolver's data (the resolver receives the user, runs after the access check, and only for the open tab). With a registered user tab open, the overview's data is not queried (D-016): a test records queries with `DB::listen` and asserts that none reads a table only the overview loads (the SSO identities table, which only the overview's `ListSsoIdentitiesAction` reads; asserted through `Tables::name('sso_identities')`, never a literal `roster_*`); tables the screen's access check also reads (memberships, roles, assignments) are not asserted on. A control request to the overview in the same test must read that same table, and the test fails if it does not, so the assertion can't pass vacuously. No loader seam is added to the controller for this.
13. The user screen's existing redirects back to the page (success and validation errors) are unchanged (D-020): `overview` is the default when `tab` is absent, so they already land on it, and no tab visibility check runs while building a redirect. A test with a visible user tab registered posts one user screen form and one failing-validation post, asserts neither redirect target has a `tab=` parameter, and follows the first to the overview. Host forms inside a registered tab supply their own routes; Roster adds no tab-specific routes.
14. The organization and user tab bars render through one shared partial, using only Atrium components and safelisted utilities (`tests/Feature/Ui/StylesTest.php` passes). The active tab is the one rendered with `aria-current="page"` by `x-atrium::icon-button`; inactive tabs render without `aria-current` (no assertion on the variant's rendered class). A test registers the same tabs on both screens (same keys through `Tabs::organization()` and `Tabs::user()`, one fixture), renders both and asserts on the response HTML that the same `data-testid` set appears and that only the open tab's element carries `aria-current="page"`; `aria-current` is the only active-state signal asserted (no styling assertion). Before the refactor, a characterization test asserts the organization bar's exact built-in `data-testid`s in order and the `href` of each `?tab=` link, and it runs unchanged against the extracted partial.
15. The organization tab bar's markup, `data-testid="tab-{name}"` ids and `?tab=` URLs are unchanged for built-in tabs; the existing organization feature and browser tests pass unmodified (`composer test` excludes the Browser suite via `--exclude-testsuite=Browser`, so `composer test:browser` runs in addition and is part of done). `OrganizationUiController::TABS` was private, so moving its keys to `Tabs::ORGANIZATION_TABS` breaks no consumer.
16. Deleted organizations and users keep rendering their deleted page; registered tabs never render there. `?tab={registered key}` on a deleted record answers 200 with the deleted page and ignores `?tab=` (D-011); no resolver or authorize closure runs, asserted with counting closures.
17. Documentation promises are checked by one documentation test that greps the README and the bundled Boost skill (`resources/boost/skills`) for a short list of exact strings (D-019): `Tabs::class`, `vendor.key` and `boot()`. It checks strings only, not prose wording, and only inside the section under a `Registered tabs` heading in each file, so unrelated mentions cannot satisfy it; a section runs from its `Registered tabs` heading to the next heading of equal or higher level. The other README promises (criteria 3, 9, D-021, D-022) are reviewed manually, not tested. The CHANGELOG upgrade note also names the Atrium version that provides `Icons::has()`, since Roster requires Atrium as `dev-main` and cannot enforce a minimum. The README additionally carries the registration example for both screens, the promises of criteria 3 (new built-in keys in minor releases) and 9 (cheap, non-throwing `authorize` closures; resolver and view errors surface as page errors), that a missing view or component fails only when the tab renders (D-021), and, with a CHANGELOG upgrade note, that consumers who published the views (`roster-views`) get no registered tabs until they re-publish or merge them (D-022).
18. Required tests: `tests/Unit` for `TabDefinition` and `Tabs` (criteria 1 to 5), `tests/Feature/Ui` for both screens (criteria 6 to 16), and `tests/ArchTest.php` passes with the new classes (final, strict types). Done means `composer test` and `composer test:browser` pass.

## Design

**`Atrium\TabDefinition`** (final, mirrors Atrium's `WidgetDefinition`):

- `final public function __construct(public readonly string $key)`, `static make(string $key)`; the key is validated against `^[a-z0-9][a-z0-9._-]*$`.
- `public private(set) string $label` (defaults to the key), `?string $icon` (Atrium icon name; default `squares-2x2`), `?string $view`, `?string $component`, `?string $permission`.
- Private `?Closure $resolver` (`Closure(Model $record): array<string, mixed>`) and `?Closure $authorize` (`Closure(Request, Model $record): bool`).
- `resolveData(Model $record): array` and `allows(Request $request, Model $record, ?OrganizationModel $scope, ?Model $self): bool` — the permission goes through `ScreenAccess::allows($permission, $scope, $self)`, then the closure, with a throwing closure counting as denied and reported once per request per key.

**`Atrium\Tabs`** (final, singleton bound in `RosterServiceProvider::register()`):

- `organization(TabDefinition $tab): self`, `user(TabDefinition $tab): self` — validate and keep in registration order, keyed by `key`.
- `organizations(): array<string, TabDefinition>`, `users(): array<string, TabDefinition>`, `flush(): void` (tests only).
- Reserved keys: `ORGANIZATION_TABS` (public, keys only: the built-in organization keys, formerly the keys of the private `OrganizationUiController::TABS`; the controller keeps a private key => permission map whose keys a test checks against it, D-023) and `USER_DEFAULT = 'overview'`.

**`OrganizationUiController::show()`**: read `tab` as a string or null. After building built-in `$tabs`, append visible registered keys. The default tab comes from the visible built-in tabs only (`$tabs[0] ?? 'settings'` is computed before registered keys are appended). Visibility is computed once and reused for the bar and the `?tab=` check. A requested registered key the viewer can't see aborts 403 via the same path as built-in tabs. When the open tab is registered, pass `registeredTab` (the definition) and its resolved data, resolved after the access check, into the `roster::ui.partials.registered-tab` partial with variables `organization`, `tab`, `tabs`, `registeredTab` and `errors` (resolver data spread first, Roster's keys last). The partial renders `@include($tab->view, [...])` or `<x-dynamic-component :component="$tab->component" ...>`.

**`UserUiController::show()`**: read `tab` as a string or null; compute visible user tabs; when none, unchanged. Otherwise pass `tabs` (`overview` + visible keys) and `tab`. When the open tab is registered, skip loading the overview's data and render the registered tab through the same partial and variable set. All current page content moves unchanged into `overview`; the page's redirects are unchanged (D-020).

**Shared tab bar** (in-scope refactor): extract the organization nav (`resources/views/ui/organizations/show.blade.php:15-26`) into `roster::ui.partials.tabs`, taking the tab list (key, label, icon), the open tab and a route closure/name. Built-in labels/icons and markup stay as today; registered ones come from the definition (labels as given, escaped; the host translates).

No config, events, migrations, HTTP or MCP surface (D-001). Registered tabs exist only on Atrium screens, so they only show while `roster.ui.enabled`.

## Out of scope

- Tabs on team, role or other screens (D-002).
- Tabs on deleted record pages.
- HTTP API / MCP equivalents (D-001).
- Config-driven or auto-discovered tab registration (registration is by code, from `boot()`).
- Sandboxing host views, components, resolvers or closures beyond criterion 9's `authorize` handling.
- Reordering, hiding or overriding built-in tabs.
- Lazy or async loading of tab bodies in the browser (tabs are full page loads via `?tab=`). Criterion 12 is the only server-side skipping: the user overview's data is not loaded while a registered tab is open.
- Ordering controls (priority, position, placing a tab before built-ins) and registered tabs as a screen default (criterion 8).
- Per-tab badges or counts, tab grouping or nesting.
- Tab-specific routes or POST actions (host forms bring their own routes).
- Translation of labels by Roster (the host translates).
- Caching of resolver output.
- Deregistering or replacing a tab at runtime (`flush()` exists for tests only).
- Registration through the `Roster` facade or a plugin (D-005).
- Registered tabs on any route other than the two show screens, including the Atrium dashboard nav, and deep links or history for them.
- Auditing or Keen events for tab views.
- Cortex / MCP redirect domains for registered tabs.
- Per-request or Octane re-registration support (registration is once, from `boot()`).

## Risks and open questions

- The user screen's default tab key `overview` is new and reserved; a host that wants that key can't use it.
- Registered tabs are mutable singleton state; registering outside a provider's `boot()` (for example per request under Octane) leaks across requests, so the README directs registration to `boot()`.
- Host view errors surface as page errors on the Roster screen; Roster doesn't sandbox them. A registration with a missing view or component only fails when someone opens the tab; Roster doesn't check that it exists (D-021), since views can be registered after the tab.
- A tab with neither `permission()` nor `authorize()` is hidden (D-024); `public()` opts in to showing it to everyone who can open the screen, and the README warns that its host view may show more sensitive data than the screen.
- Two packages registering the same `vendor.key` makes the second `boot()` throw, which can stop app boot; the exception message names the key and the screen so it is diagnosable (criterion 3).
- Consumers who published the views (`roster-views`) keep their copies: they get no registered tabs, no `overview` wrapper and no shared tab bar, with no error. The README and a CHANGELOG upgrade note tell them to re-publish or merge (D-022).
