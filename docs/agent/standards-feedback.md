Follow-up: the standard should name these two plain fallbacks. **Resolved 2026-11-23** (2026-11-23-0943-roster-v2-api-and-mcp-only): Roster v2 ships no Atrium views, so `roster/atrium-views` and `StylesTest` are deleted; the plain invitation page and banner are the only views left, and `tests/ArchTest.php` asserts `resources/views` holds exactly those three files |
| 2026-11-23 | 2026-11-23-0943-roster-v2-api-and-mcp-only | http/authorization | `LookUpInvitationRequest` overrides `authorize()` to return `true` (its `ability()` is empty), so the public `GET {prefix}/invitations/{token}` needs no signed-in user and no permission | The token is the only credential: the guest opening an invitation link is not signed in yet. `InvitationResponseRequest` already overrides `authorize()` for the same reason. Enumeration is countered by the 48-alphanumeric route constraint, one identical 404, `Cache-Control: no-store` and the per-IP `roster-invitation-lookup` limiter. Follow-up: the standard should name token-credential requests as the exception |
| 2026-11-23 | 2026-11-23-0943-roster-v2-api-and-mcp-only | actions/actions-events (Roster: starting/finished events that took input carry the Data) | `InvitationLookingUpActionEvent` carries nothing and `InvitationLookedUpActionEvent` only the invitation; neither carries `LookUpInvitationData` | The Data holds the plain token, which must never reach listeners, queued payloads or the audit log; a test serializes both events and searches them for it. Follow-up: the standard should allow leaving out Data that holds a credential |
| 2026-11-23 | 2026-11-23-0943-roster-v2-api-and-mcp-only | http/authorization ("How the Authorizer answers") | `Authorizer` and `Resources` live in `Support\Authorization` (not `Domains\Permission\Services`), `Authorizer::RESOURCES` holds five core resources (no `roles`), registered by `RosterServiceProvider::register()`; `Authorizer::check()` no longer remembers its answers for the request (only the resolved policy per ability, until `Resources::generation()` changes, and the owned organizations and record parents, until an organization is written) | Criterion 33: every check goes through Keystone's `Permissions` contract, which has no `generation()`, so the Authorizer cannot tell when a role store has forgotten anything; remembering answers would go stale after `Permissions::forget()`.
