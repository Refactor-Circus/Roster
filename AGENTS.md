# Roster

This repository is a Laravel package. Keep the package focused, idiomatic, and easy for Laravel developers to install, test, and maintain.

## Package Conventions

- Use Laravel-native package APIs and the existing service provider shape before adding abstractions.
- Keep package names, namespaces, Composer metadata, publish tags, documentation, and examples aligned with `refactor-circus/roster`.
- Add only the files and dependencies needed for the package behavior being implemented.
- Prefer explicit Laravel package code over helper abstractions unless the extension point is real.
- Keep tests focused on observable package behavior through public APIs, service provider wiring, commands, routes, published resources, and documentation promises.

## Architecture

- Roster stands on `refactor-circus/keystone`, the suite's shared runtime. `RosterServiceProvider` extends `RefactorCircus\Keystone\Support\PackageServiceProvider`, describes the package in `definition()` (key `roster`, `RosterServer`, authorization on by default, history guarded by `roster.audit.view`), calls `registerPackage()` right after merging config, and boots the MCP server, Cortex and the shared history route (`GET {prefix}/history`, `roster.history.index`) through the base helpers. Action events implement `RefactorCircus\Keystone\Contracts\ActionStartingEvent` / `ActionFinishedEvent`; finished events wait for the surrounding transaction to commit.
- Code lives in domain modules under `src/Domains/{Domain}` (User, Organization, Team, Invitation, Role, Permission, Impersonation, Sso, Scim, Transfer), mirroring the `mono` domain-module standard. Each domain has a `{Domain}ServiceProvider` (extending `RefactorCircus\Keystone\Support\ServiceProvider`) registered by `src/Domains/DomainServiceProvider.php`, its JSON API routes in `routes.php` (loaded with `loadApiRoutesFrom()`), any browser routes in `web.php` (`scim.php` for the SCIM protocol), and only the subdirectories it uses.
- Action input is a `final readonly` `{Action}Data` in the domain's `Data/` (on `RefactorCircus\Keystone\Data\Data`), never an array: fields are promoted constructor properties (camelCase of the input keys; enums for enum values; `T|Missing = new Missing` for partial updates), `rules()` lives on the Data (with any context args), and the starting/finished events that took input carry the Data (the status events carry just the reason). HTTP and MCP requests validate once: their `rules()` return the identifier rules plus `XData::rules(...context)` (identifiers first, so they win), and `persist()`/`handle()` build with `XData::fromValidated($this->validated() / $validated)` - never `XData::from()` in a request (ArchTest). Atrium controllers and other untrusted input use `XData::from($request->all(), ...context)`, which validates; code that vouches for its values uses `new XData(...)`. `tests/ArchTest.php` rejects array input on `execute()`.
- API resources extend `RefactorCircus\Keystone\Http\Resources\JsonResource` and declare `schema(JsonSchema $schema)` next to `toArray()` (always-present fields `required()`, conditional ones not, `nullable()`, enum values listed; nullable enums include `null`). MCP requests answer with `(new XResource($m))->additional([...])->toStructuredResponse()` / `XResource::collection($page)->toStructuredResponse()`, and each tool declares `outputSchema()` as `XResource::structuredSchema($schema)` / `collectionSchema($schema)` plus its extra keys. `mcpTool()` in tests checks every structured answer against the tool's schema with Keystone's `Testing\StructuredSchema`, and `tests/Feature/Mcp/OutputSchemaTest.php` requires the declaration.
- Models use Keystone's `DispatchesModelEvents` (one `{Entity}{Hook}Event` per Eloquent hook, soft-delete hooks only on soft-deleting models) and resolve their table with `getTable()` from `Support\Tables` (`roster.tables`, on Keystone's `Database\Tables`); migrations, pivots, `Rule::unique`/`exists` (by model class) and joins use the same keys, never literal `roster_*` names (`tests/ArchTest.php` checks with `Arch::literalTableNames()`, and that every model has a policy in `roster.policies` with `Arch::modelsWithoutPolicies()`). Every Action and Impex flow step dispatches a starting and a finished event, the starting one before and the finished one after a `DB::transaction()` that holds all of its writes (side effects that must not survive a rollback - Impex signals, jobs, mail - go after it or `afterCommit`). `tests/ArchTest.php` checks all three with Keystone's `Testing\Arch` (`actionEventGaps()`, `writesOutsideTransactions()` and `modelEventGaps()` over every model); `parityGaps()` uses `Testing\Parity`, and `mcpTool()` is `Testing\McpTools::call()`.
- Models are named `{Entity}Model`; their pre-domain class names (`RefactorCircus\Roster\Models\{Entity}`) are kept as morph aliases in each domain provider, so stored subject types and other stored values keep the same string.
- Authorization: `Http\Request` and `Mcp\Request` extend Keystone's request bases and use `Support\Concerns\AuthorizesWithRoster`, whose `authorize()` checks the request's `ability()`, `scope()` and `self()` through `Domains\Permission\Services\Authorizer` (Keystone's base answers guests 401). The domain request bases carry the defaults: organization requests are scoped to `organization()`, each MCP base's `rules()` returns its identifier rules (`userRules()`, `organizationRules()`, `teamRules()`, `roleRules()`, `connectionRules()`, `transferRules()`), and the User/Organization bases find deleted records with `trashedUser()` / `trashedOrganization()`; a request only overrides what differs. `Authorizer::check()` refuses impersonation-blocked permissions, then sends `roster.{resource}.{verb}` to the Gate policy of the resource's model (`Authorizer::RESOURCES`, method = camel-cased verb, arguments `[ModelClass, $scope, $self]`); the bundled policies (`Domains/{Domain}/Policies`, on `Support\Policies\Policy`, registered from `roster.policies` by `registerPolicies()`) answer with `Authorizer::permits()`, the raw permission check. Every model has a policy. `Authorizer::check()` answers are remembered for the request and dropped whenever `Permissions` forgets anything (`generation()`); policies asked with a record get its organization/team from `Authorizer::parentOf()`. Writes that change one user's access call `Permissions::flushUser()`, not `flush()`; `roster.permission_cache` optionally keeps permission names and grants in the cache store, cleared by the same listener. MCP tools extend `RefactorCircus\Keystone\Mcp\Tool`; `RosterServer` extends `RefactorCircus\Keystone\Mcp\Server` and lists `Mcp\Tools\ListRosterHistoryTool`.
- Roster has no audit code beyond its Keen integration, and that only runs while Roster audits: Keystone's `Package::audits()` (refactor-circus/keen installed and `roster.audit.enabled` on; `Roster::auditing()` asks it). Then, once every provider has booted, `Support\Audit` registers what Roster knows on Keystone's `AuditHooks` (labels, snapshot extras - profile fields, role permissions, organization domains, assignment slugs - the subject picker and organization scope for Roster's events, the impersonator/transfer/SCIM token context for every entry, and the password column's redaction), and `viewAuditLog` is defined as global `roster.audit.view` unless the app defines it. Otherwise Keen ignores Roster's events, the history route answers 404, the history tool is not offered, and Atrium shows no history. Never add audit tables, writers or audit APIs to Roster. `RosterServiceProvider` names the `scim` and `web` route surfaces on Keystone's `Surface` either way.
- Atrium owns every component and style. Roster ships no stylesheet and no Blade component namespace: views use `x-atrium::*` components and the utilities safelisted in Atrium's stylesheet only, with no `<style>` blocks or `style=` attributes (`tests/Feature/Ui/StylesTest.php` checks with `AtriumStyles`). Shared bits are plain partials (`ui/partials/status-dot`). The only exceptions are the two plain views shown without Atrium, `invitations/show` and `partials/impersonation-banner-plain` (inline styles; `StylesTest` excludes exactly those two); `roster::impersonation-banner` includes the plain one or `ui/impersonation-banner` (Atrium's banner in standalone mode) by `$rosterUsesAtrium`.
- Atrium is optional (`suggest` and `require-dev`, with a `conflict` on `refactor-circus/atrium` `<0.1.0`). `RosterServiceProvider` registers `Atrium\AtriumServiceProvider` only when `class_exists('RefactorCircus\Atrium\Atrium')` (a string, never `::class`) and `RosterServiceProvider::$withoutAtrium` is false; that seam rebinds `Domains\Invitation\Contracts\InvitationPage` (default `PlainInvitationPage`) to `Atrium\InvitationPage`, registers `@rosterCan` and shares `rosterUsesAtrium`. Nothing outside `src/Atrium` names an Atrium class (`tests/ArchTest.php`), and `tests/Modes/AtriumUnavailable` (`AtriumUnavailableTestCase`) plus the CI `without-atrium` job prove Roster boots and serves its API, MCP server, invitation page and banner without it.
- Screens declare themselves. Every dashboard screen (and the Atrium invitation page) builds `Screen::standard($key, $kind)` through `AuthorizesScreens::screen()`, with its record and the access closure `ScreenAccess::allowsOn($permission, $record)`, resolves it with `Atrium::screens()->resolve()` only after its own authorization, passes it to the view as `resolved`, and renders `x-atrium::screen-tabs`, `x-atrium::screen-tab-panel` and the sections of every declared slot. Other packages add tabs and sections through Atrium's registry; Roster renders no other package's UI (no audit trail, history navigation, MCP or redirect-domain screens) and has no tab registry of its own. The organization screen's built-in tabs are `members`, `teams`, `invitations`, `roles`, `sso`, `scim` and `settings`; every other screen has `overview`. A new record type needs a row in `ScreenAccess::allowsOn()`, which refuses unknown models.
- Cross-domain code stays outside the domains: `Roster`, the facade, `RosterServiceProvider`, `Http\Request`, `Http\Controllers\TrashController`, `Console\Commands\PurgeDeletedCommand`, `Mcp\Request`/`RosterServer`/`Tools\ListRosterHistoryTool` and the `Mcp\Concerns` schema traits, `Support/` (`Users` - email lookups exact first, then `CaseInsensitive` -, `Scopes`, `Slugs`, `UserKey`, `Tables`, `Policies\Policy`, `Concerns\ResolvesScopes`, `Concerns\AuthorizesWithRoster` - the authorization both request bases share), and `Atrium/` (dashboard screens, `ScreenAccess`, `RosterSupportFeature`, `AtriumServiceProvider` and the Atrium `InvitationPage`). `Support\Audit` holds the Keen hooks.
- The Impex flows (`Transfers\Flows\*`) keep their pre-domain class names: Impex stores them on every run and batch and replays in-flight imports by them.

## Quick Commands

- Full validation: `composer test`
- Formatting check: `composer lint:check`
- Static analysis: `composer analyse`
- Pest tests: `composer test:unit`
- Browser tests: `composer test:browser`
- Workbench build: `composer build`
- Workbench server: `composer serve`
